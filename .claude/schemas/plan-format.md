# plan.md Format (File-Level Tactical Plans)

Version: 1.0

## Purpose

`plan.md` is an optional per-spec file/symbol-level change map, generated by the
tasks-list-creator agent in the same exploration pass that produces the task list. It exists so
that N implementers don't each re-discover the codebase from scratch, and so scope drift is
caught mechanically instead of policed by hand.

**It is a contract with an amendment process, not a prophecy.** Plans predicting the future go
stale; plans that implementers are required to amend before deviating stay true. `plan.md` is
therefore true-at-end by construction — read it together with its `## Amendments` section, never
the task-keyed sections alone.

## When it exists

Only above the scope gate: specs whose total change map is more than ~3 distinct files (see the
scope-gate rule in `tasks-list-creator.md`). Smaller specs skip `plan.md` entirely and get inline
`files: [path1, path2]` annotations on each task title instead. **No `plan.md` means every
downstream consumer (spec-start, verify-spec) behaves exactly as it does today** — this format is
strictly additive.

## Location

`.mm/specs/{spec-folder}/plan.md`

## Frontmatter

```yaml
---
spec: 2026-07-08-file-level-tactical-plans-plan-md-change-map
planning_head: a1b2c3d4e5f6...
generated: 2026-07-08T14:32:00Z
---
```

- `spec` — the spec folder slug this plan belongs to.
- `planning_head` — `git rev-parse HEAD` of the code checkout at the moment the plan was
  generated. This is the freshness anchor: consumers diff it against current HEAD to detect
  planned files touched by commits that landed after planning.
- `generated` — ISO-8601 timestamp of generation.

## Task-keyed sections

One `## {task-id}: {task title}` section per task, in the same order and using the same task IDs
as the task list. Each line under a section is one change-map entry:

```
ADD|MODIFY|DELETE {path} — {symbol} — {one-line what}
```

- `{path}` — real, repo-relative file path. Must be a path that exists (for MODIFY/DELETE) or a
  path that will be created in a real, verified-to-exist directory (for ADD). Never a guess.
- `{symbol}` — the function, type, component, route, or other named unit being touched. For
  whole-new-file ADDs where no symbol exists yet, name the primary export/entry point instead.
- `{one-line what}` — the change, in one line. Not a paragraph, not a code snippet.

Optional `reuse:` follow-up lines under any entry:

```
reuse: {path}:{line} — {pattern to follow}
```

Points the implementer at a real, cited existing pattern rather than re-deriving one from
scratch.

### Example

```markdown
## T2: Add priority field to task API

ADD|MODIFY|DELETE src-tauri/src/commands/tasks.rs — create_task — accept optional `priority` param, default "medium"
reuse: src-tauri/src/commands/tasks.rs:88 — existing param-with-default pattern in update_task
MODIFY desktop/monday-morning/src/lib/types.ts — Task interface — add `priority: 'low' | 'medium' | 'high'`
```

### Interface-first entries (required at boundaries)

Where two tasks meet at a boundary — a Rust command and the frontend type that consumes its
response, an MCP tool and its caller, a store and the component reading it — the entry on **both**
sides of the boundary MUST state the contract itself (function signature, or the JSON/TS shape),
not just the filename. This is what makes the two tasks safe to execute in parallel: each side
can conform to the stated shape without reading the other side's code first. A boundary entry
that says only "MODIFY tasks.rs — update the response" is not interface-first and should be
rejected; it must say what the response shape becomes.

## Granularity rule

File + symbol level, **never** line-level, **never** pseudo-code or code blocks embedded in
entries. Line-level plans rot within hours of a refactor; file+symbol plans survive them. If you
find yourself writing more than one line of "what", the entry is too fine — collapse it back to
one line describing the outcome, not the steps.

## `## Amendments`

A single section at the bottom of the file, appended to (never rewritten) as implementation
proceeds:

```markdown
## Amendments

AMEND T2: MODIFY src-tauri/src/commands/notifications.rs — reason: priority change requires a notification-copy update not foreseen at planning time
```

An implementer that discovers it must touch a file the plan didn't mention appends an `AMEND`
line **before** touching that file — not after, not as an afterthought during retro. Format:

```
AMEND {task-id}: {ADD|MODIFY|DELETE} {path} — {reason}
```

Amendments are not failures; unrecorded drift is. A plan with a healthy amendment log did its
job — it gave implementers a real starting map and a paper trail for the parts reality corrected.

## Consumers

- **spec-start** — passes each task its own section as the allowed-paths contract (the planned
  file set for that task IS the scope the implementer is told to stay within); does a cheap
  freshness check (`planning_head` vs current HEAD) before execution; derives same-file batching
  and parallel-safety from pairwise file-set intersection across task sections.
- **verify-spec** — reverse coverage: promised files (task sections + `## Amendments`, i.e.
  post-amendment) vs. actual diff files is mechanical set arithmetic. Files in the diff but not in
  the promised set (and not amended) are scope drift with high confidence.

Keep this file a reference, not an essay — if you're adding prose explaining why a rule exists
beyond one sentence, it probably belongs in the spec instead.
