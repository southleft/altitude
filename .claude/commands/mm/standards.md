# Generate Coding Standards

Analyze the project's codebase and generate per-project coding standards in `.mm/standards/`.

## Phase 1: Check Existing Standards

Check if `.mm/standards/` already has files.

**If standards exist:**

1. Read all existing standards files
2. Summarize what's already captured
3. Ask the user:
   > Standards already exist for this project. Would you like to:
   >
   > 1. **Update** — Re-analyze the codebase and refresh existing standards
   > 2. **Add** — Generate standards for a specific domain (e.g., testing, API)
   > 3. **Review** — Walk through current standards and refine them
4. Proceed based on their choice

**If no standards exist**, proceed to Phase 2.

---

## Phase 2: Analyze Codebase

Use the **Explore** subagent to analyze the codebase. Focus on detecting actual patterns, not imposing theoretical ones.

### What to Detect

For each applicable domain, look for:

**Naming (`naming.md`)**

- File naming: kebab-case, camelCase, PascalCase?
- Variable/function naming conventions
- Component naming patterns
- Constants naming (UPPER_SNAKE, etc.)
- Examine at least 10-15 representative files across different directories

**Components (`components.md`)**

- Component file structure (single-file, split, barrel exports?)
- Props/state patterns
- Event handling conventions
- Composition vs. inheritance patterns

**Architecture (`architecture.md`)**

- Directory structure conventions
- Module boundary rules (what imports what)
- Dependency direction (UI -> services -> data, etc.)
- Where shared code lives vs. feature-specific code

**Error Handling (`error-handling.md`)**

- Try/catch patterns
- Error types (custom classes, union types, Result patterns?)
- Logging conventions
- Validation approach (where, how)

**Testing (`testing.md`)**

- Test file location (co-located, separate directory?)
- Test naming conventions
- Testing framework and utilities
- Mocking approach
- What gets tested (unit, integration, e2e)

**Styling (`styling.md`)**

- CSS approach (utility-first, CSS modules, styled-components?)
- Class naming conventions
- Theme/design token usage
- Responsive patterns

**Types (`types.md`)**

- Type definition location and organization
- Interface vs. type alias conventions
- Generic usage patterns
- Enum vs. union type preferences

**API (`api.md`)**

- Endpoint naming conventions
- Request/response patterns
- Authentication patterns
- Error response format

### Detection Rules

- Only generate a standards file for domains that have clear, detectable patterns
- Skip domains where the codebase is too small or inconsistent to establish a pattern
- Look at **actual code**, not just config files
- Note where the codebase is inconsistent — these are the most valuable standards to establish

---

## Phase 3: Present Findings

Present the detected patterns to the user, organized by domain. For each domain:

```
### [Domain]

**Detected patterns:**
- Pattern 1 (seen in X files)
- Pattern 2 (consistent across module Y)

**Inconsistencies found:**
- File A uses approach X, but file B uses approach Y

**Recommendation:** [what the standard should be]
```

Ask the user to confirm, correct, or skip each domain. This is a conversation — they may have context about why something looks inconsistent (intentional vs. tech debt).

---

## Phase 4: Generate Standards Files

Create `.mm/standards/` directory if needed. For each confirmed domain, create a standards file.

### File Format

```markdown
# [Domain] Standards

> Auto-generated by `/mm:standards` on {YYYY-MM-DD}. Updated by user corrections.

## Conventions

- **Convention name**: Description with rationale
```

// Example

```

- **Convention name**: Description with rationale
```

// Example

```

## Patterns

### [Pattern Name]

[Description of when and how to use this pattern]

```

// Code example from the actual codebase

```

## Anti-patterns

### [Anti-pattern Name]

[What to avoid and why]

```

// Bad example

```

```

// Good alternative

```

```

### Writing Rules

- Use **actual code examples** from the codebase, not generic samples
- Include the **why** behind each convention — this helps Claude make judgment calls in edge cases
- Keep it concise — standards files should be quick to scan, not exhaustive documentation
- Only document things that aren't self-evident from reading the code

---

## Phase 5: Confirm

After generating all files, output:

```
Coding standards generated!

Created:
- `.mm/standards/naming.md` — File and variable naming conventions
- `.mm/standards/components.md` — Component structure and patterns
- [etc.]

These standards are now automatically applied when writing code in this project.

To update: Run `/mm:standards` again or edit the files directly.
To add a domain: Run `/mm:standards` and choose "Add".
```
